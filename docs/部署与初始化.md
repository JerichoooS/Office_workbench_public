# 部署与初始化指南

> 第一次部署、给同事部署、或者重建环境时，按这份文档一步步来。
> 开发约定见 [开发规范.md](开发规范.md)。

---

## 一、第一次部署（全新环境）

1. **准备代码**：整个项目文件夹（从 GitHub 拉取，或者直接拷文件夹都可以）。
2. **在 WorkBuddy 创建并部署应用**：language=node，startCmd=`node server.js`，installCmd 留空（零依赖）。部署完成后会得到一个线上地址。
3. **云服务激活**：WorkBuddy 会生成 `public/config.js`（公开配置），这个文件不要手改。
4. **先用微信登录一次线上地址**：这一步会在数据库里留下你的账号。下一步要靠它认定「管理员是谁」，所以必须先登录。
5. **建表**：让 WorkBuddy 按顺序、逐条执行：
   - `db/migrations/001_init.sql`
   - `db/migrations/001_rls.sql`
   - `db/migrations/002_push.sql`（执行前先确认 `SELECT owner_id FROM user_settings` 只有你自己一行）
   - `db/migrations/004_ai_features.sql`
   - `db/migrations/005_phase2.sql`（函数体和 DO 块里的分号属于同一条语句，不要拆开；任何一条报错就停下，不要执行最后一条）
   - 执行完再跑一次只读核对 `db/checks/005_check.sql`，19 项应全部为 true。
6. **选择推送口令方式**（见第二节），按所选方式完成设置。
7. **重新部署一次**，然后按第三节在手机上测试。

---

## 二、选择「推送口令」方式（必选其一）

**为什么要选**：到点提醒、早晚报要在你没打开网页时由服务器发出。服务器去数据库取「谁有到期提醒、推给哪台手机」时，需要一个口令证明自己是服务器。WorkBuddy 平台没有「环境变量」可以安全地存放这个口令，所以有两种存放方式，按需选择。

| | 方式一：口令文件 | 方式二：管理员交接（默认） |
|---|---|---|
| 口令放哪 | 项目里的 `server/server-token.txt`，随代码一起部署 | 只在数据库里；你登录工作台时，工作台自动交给服务器，服务器只放在内存里 |
| 服务器被平台重启后 | **自动恢复**，推送不中断 | **推送暂停**，直到你下次打开工作台（任何设备）；6 小时内错过的提醒随后补发，早晚报超过设定时间 3 小时不补 |
| 安全性 | 能看到项目文件（或私有仓库）的人就能拿到口令。口令不能登录、不能改删待办和项目，但能做的不止读提醒（见表下「口令能做什么」） | 项目里没有任何密钥 |
| 需要做什么 | 生成口令文件，并让数据库认它（见下） | 什么都不用做 |
| 适合 | 自己用，项目只在自己手里，最在意提醒不漏 | 分享给别人、项目放公共位置、或不想在项目里放任何密钥 |

> 不确定就先用**方式二**，它不需要任何操作；以后想切换到方式一，随时可以。
>
> 实际运行发现：WorkBuddy 平台在没有重新部署的情况下也可能自行重启服务。方式二下每次重启都会让推送暂停到管理员下次打开应用，期间的提醒会以「补发」形式晚到。**对提醒准时性有要求时，请用方式一。**

**口令能做什么**（= `db/migrations/002_push.sql` 里服务器专用函数的全部能力；谁拿到口令，谁就能做这些。两种方式用的是同一种口令，区别只在放哪）：

- **读**：所有开了早/晚报、且有设备订阅推送的用户的未完成待办（以及 2 天内完成的）的标题、状态、优先级、截止时间；到期提醒对应的待办标题、所属项目名称和起止日期、等待对象的名称、用户时区；各设备的推送订阅（地址和密钥）；推送签名密钥（含私钥）。
- **写**：认领到期提醒（读出的同时标记为「已发」，之后不会再推送）；给「等待他人」的待办加一次催办；删除推送订阅；把某天的早/晚报标记为已发；推送签名密钥为空时写入一次。
- 所以拿到口令的人可以**冒充本站给你的设备发通知**，也可以**让你收不到提醒和早晚报**。
- **做不到**：登录；读备注、进展记录、联系人电话等资料、材料收集、AI Key；新建、修改或删除待办、项目、联系人。
- 本机调试（`start-mac.command`，HOST=127.0.0.1）默认不读口令文件、不跑推送调度，免得本机抢先认领线上提醒；确需在本机测推送时用 `WB_PUSH=1`。

### 方式一：口令文件（步骤）

1. 在项目文件夹里运行：
   ```bash
   node tools/new-server-token.js
   ```
   它会生成 `server/server-token.txt`，并在屏幕上打印一条 `UPDATE server_config …` 的 SQL。
2. 把这条 SQL 交给 WorkBuddy 执行（在 `002_push.sql` 之后执行）。旧口令随即失效。
3. 让口令文件随代码部署：
   - **拷文件夹部署**：文件已经在文件夹里，直接部署即可。
   - **从 GitHub 部署**：仓库**必须是私有的**。从 `.gitignore` 里删掉 `server/server-token.txt` 这一行，由你自己提交并推送。默认它被忽略，是为了防止口令被误传。
4. 重新部署。部署后访问 `你的地址/api/push/status`，应返回 `{"push":"on"}`。

### 方式二：管理员交接（步骤）

1. 确认 `002_push.sql` 已执行，且执行时 `user_settings` 里最早的一行是你（管理员 = 那一行的账号）。
2. 部署后用微信登录工作台一次。之后 `你的地址/api/push/status` 会从 `locked` 变成 `on`。
3. 以后平台若重启了服务，打开一次工作台即可恢复。

### 切换与换口令

- 方式二 → 方式一：按「方式一」步骤做即可。
- 方式一 → 方式二：删掉 `server/server-token.txt` 后重新部署（数据库里的口令仍然有效，由你登录时交接）。
- 怀疑口令泄露：重新运行 `node tools/new-server-token.js` 并执行它打印的 SQL，旧口令立即作废。

## 三、手机测试（iPhone，需 iOS 16.4 以上）

1. 用 Safari 打开线上地址，微信登录；
2. 点底部「分享」→「添加到主屏幕」；
3. **从主屏幕图标打开**（不要从 Safari 打开）；
4. 设置 → 本机接收通知 → 开启通知 → 允许；
5. 点「发测试通知」，几秒内应收到；
6. 回首页记一条「2分钟后提醒我测试推送」，锁屏等待；点通知应直接打开这条待办；
7. 第二天按设定时间留意早报。

## 四、给同事部署（不需要会用 GitHub）

1. 把项目文件夹拷给同事，**先删掉** `server/server-token.txt` 和 `db/migrations/003_server_token.sql`（如果有）。绝不能共用口令，每个部署各用各的。
2. 同事在自己的 WorkBuddy 里，按「第一节」从头部署，包括先登录一次再执行 002。
3. 推送口令建议用方式一：在同事自己的部署目录里生成口令文件（`node tools/new-server-token.js`），平台重启后提醒不中断；口令文件只留在那台电脑上，不要提交到任何仓库。不想管口令就用方式二，什么都不用做。
4. 同事的数据在自己的云数据库里，和你的完全隔离。

---

## 五、升级已经部署过的工作台（拉取新版本）

1. 先让 WorkBuddy 把云库里的数据整份导出一份留底（所有表），记下存在哪里。
2. 把最新代码拉到原来的部署目录。本地的 `public/config.js`、`server/server-token.txt`（如果有）保留不动。
3. 按编号执行还没执行过的迁移文件：`SELECT version FROM schema_migrations` 能看到执行过哪些；没有这张表，说明 005 还没执行。004 重复执行也安全。
4. 用原配置重新部署到原来的应用（同一个地址，**不要新建应用**）。
5. 访问 `你的地址/api/push/status`，push 应为 `on`（方式二要先打开一次工作台）；再执行只读核对 `db/checks/005_check.sql`，19 项应全部为 true。
