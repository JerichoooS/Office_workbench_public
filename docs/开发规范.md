# 个人工作台 · 开发规范（v2）

> 给任何来维护本项目的人或 AI（包括 WorkBuddy）。**动手前先读完本文件**；改动要符合这里的约定，改了约定就同步改本文件。
> 需求有不清楚的地方，**先问用户，确认后再写代码**。

---

## 1. 项目是什么

个人工作管理应用：**任务（大）→ 待办（小）**，加上提醒推送、等待催办、材料收集。电脑和 iPhone 都要好用。

| 项目 | 约定 |
|---|---|
| 运行 | `node server.js`，零依赖，单端口（`PORT` 环境变量，默认 3000） |
| 部署 | WorkBuddy Sites；`installCmd` 留空，`startCmd` = `node server.js` |
| 登录与数据 | WorkBuddy Cloud SDK（`public/vendor/workbuddy-cloud-sdk.global.js`）：微信扫码登录 + 云数据库 |
| 前端 | 原生 ES Modules，**没有构建步骤、没有框架、没有 npm 包** |
| 外部资源 | **禁止**引用 CDN（jsDelivr、Google Fonts 等在国内不可靠）。第三方文件一律放 `public/vendor/` |
| 线上地址 | 部署后由 WorkBuddy 分配（`public/config.js` 中的 endpoint） |

## 3. 启动与本地调试

1. 本机运行：Mac 双击 `start-mac.command`，或 `node server.js`，打开 http://127.0.0.1:3000/
2. 地址是 `127.0.0.1` / `localhost` 时**自动进入本地模拟模式**：免登录、数据存浏览器 localStorage，页面顶部有「本地模拟模式」标记。
   - 首页空库时有「填充示例数据」按钮；设置页可「清空模拟数据」。
   - `?mock=0` 关闭模拟（会记住），`?mock=1` 恢复。
3. 线上域名永远不会进入模拟分支（判断在 `boot.js` 的 `isLocal`）。
4. 微信登录只能在线上地址测试（WorkBuddy 不允许本地回调）。

**改完代码的自检（每次都做）：**
- `node --check` 检查改过的 JS 文件；
- 本地模拟模式下，桌面宽度和手机宽度（375px）各点一遍改动涉及的页面；
- 浏览器控制台无报错；页面没有横向滚动。

## 4. 数据层规范

- **视图和组件不直接调用 `cloud.database`**，一律通过 `data/repos/*.js`。
- 仓储函数用 `run(builder)` 执行查询：出错会自动弹出中文提示并抛错。
- 写操作完成后调用 `changed('表名')`，当前页面会自动刷新（保持滚动位置）。
- 状态流转等有副作用的逻辑写在仓储里（例：`todos.setStatus` 负责写完成时间、生成下一次重复、排催办），视图只调用。
- 库里的枚举值用英文（`todo/doing/waiting/done`），界面文字一律从 `data/schema.js` 取中文。
- 每张业务表都有 `owner_id`，类型是 **text**（WorkBuddy 云库的 `auth.uid()` 返回 text，不是 uuid），默认 `auth.uid()`，并开启 owner-only RLS；前端**不要**手动传 `owner_id`。

### 4.1 数据表一览（详见 `db/migrations/001_init.sql`）

| 表 | 用途 | 关键字段 |
|---|---|---|
| `user_settings` | 每人一行设置 | 早/晚报开关与时间、默认提醒、AI 总开关与 Key、`ai_features`（各项 AI 功能开关，004 迁移） |
| `contacts` | 联系对象 | `kind`：person 人 / department 部门 / section 科室 / unit 单位 |
| `tasks` | **项目**（界面名称） | 起止日期、状态、`archived_at`（非空=已归档）、`source_task_id`（套用来源） |
| `task_contacts` | 项目-联系人 | 多对多 |
| `todos` | 待办（小） | `status`、`priority`(0=P0)、`due_at`+`due_all_day`、`waiting_on`、`repeat_rule`、`checklist`、`tags` |
| `todo_logs` | 进展记录 | |
| `reminders` | 提醒 | `kind`：before_due 截止前 / at_time 准时 / nudge 催办；`sent_at` 非空=已发送 |
| `collections` / `collection_targets` | 材料收集 / 收集对象 | `submitted_at` 非空=已交 |
| `tags` | 标签库 | `use_count` 用于补全排序 |
| `push_subscriptions` | 推送订阅（每台设备一行） | |

### 4.2 改表流程（必须按顺序）

1. 新建 `db/migrations/00N_说明.sql`（**不要改已执行过的旧文件**），一条语句一行块，语句之间空一行；新表要附 RLS 四条（模板见 `001_rls.sql`）。
2. 同步改 `public/app/data/mock.js` 的 `DEFAULTS` / `FK`（字段默认值、级联关系），否则本地模拟和线上行为会不一致。
3. 新枚举值写进 `data/schema.js`。
4. 在本文件 4.1 表格登记。
5. 部署前请 WorkBuddy 按编号执行新的迁移文件。

## 5. 界面规范

**设计方向**：北欧冷淡风的暖色版本——低饱和、留白、功能入口清楚。参考设计稿 `design/prototype-v2.html`。

- 颜色、字体、圆角只用 `styles/tokens.css` 的变量；**组件里不写字面颜色**。深色模式由 tokens 自动切换。
- 新主题：在 tokens.css 复制一组变量，挂到 `:root[data-skin="名字"]` 下。
- 只用系统字体（PingFang / 微软雅黑）。数字用 `.num`（等宽对齐）。
- 布局断点只有一个：**≤ 760px 为手机**（单栏 + 底部标签栏），否则为桌面（侧边栏 + 内容 + 右侧抽屉）。
- 不用浏览器 `alert / confirm / prompt`，用 `confirmSheet()`、`openSheet()`、`toast()`。
- 拼 HTML 时，**所有用户输入必须经过 `esc()`**。

**功能分级（用户确认，按使用频率摆放）：**

| 频率 | 功能 | 放在哪 |
|---|---|---|
| 每天多次 | 看今天、记一条、勾完成、改状态、记进展 | 首页、手机底部「+」、详情顶部 |
| 每周几次 | 看板、项目 | 主导航 |
| 偶尔 | 日历、材料收集、零星待办、全部待办（首页底部链接） | 首页右上角「日历」图标（底部弹出）；首页「负一屏」（从左往右滑或点左上角图标）；电脑侧边栏有「材料收集」 |
| 很少 | 推送、AI、联系人、外观、账号 | 设置页（分组列表 + 子页面） |

**首页标题行**：概览（负一屏）｜ 今天 ｜ ＋记一条（虚线圆圈，点开输入栏从下方展开）｜ 日历。负一屏的「本周概览」数字可点，列出对应待办。
**导航**：手机底部 = 首页 / 看板 / ＋记一条 / 项目 / 设置（详情、负一屏打开时底部栏自动收起）；电脑侧边栏 = 首页 / 看板 / 项目 / 材料收集 …… 设置。从任何面板里点导航，会先关闭面板再跳转。
**设置结构**：`#/settings` 分组列表 →「通知与提醒」「AI 助手」（总开关 + 每项功能开关，模型/地址在「高级」）「常用联系人」（按使用次数排序，可编辑、删除、合并重复，`contacts.mergeContact`）「账号与关于」子页面；外观直接在列表行切换。
**动效**：点按缩放反馈、切页轻微上浮（数据刷新不触发）、面板滑入滑出；系统开启「减少动态效果」时全部关闭。

详情面板同理：常用项直接显示，重复/优先级/标签/备注收进「更多设置」（折叠时仍显示当前值）。新功能先判断频率，再决定位置。

**常用组件类名**：`.btn(.primary/.small/.danger)`、`.chip(.accent/.wait/.bad/.warn/.ok/.ghost)`、`.seg`、`.switch`、`.list > .item`、`.group > .group-h`、`.card`、`.task-card`、`.placeholder`、`.form`、`.kv`、`.fold`。

**文案**：站在用户角度说话（「早报」不说「digest」）；按钮写清动作（「保存」「复制」），完成后 toast 说结果（「已保存」）；报错说清楚原因和怎么办。

## 6. 新增一个页面（步骤）

1. `public/app/views/xxx.js`，导出 `export async function mount(root, params, ctx)`：取数据 → `root.innerHTML = …` → 用 `root.onclick` 做事件委托。
2. `main.js` 里 `route('/xxx', xxx)` 注册。
3. 按 §5 的使用频率，在 `components/shell.js` 的 `PRIMARY` 或 `SECONDARY` 加入口。
4. 需要新数据就按 §4.2 走改表流程，并加 `data/repos/xxx.js`。
5. 按 §3 自检。

## 7. 业务规则（已与用户确认，改动前先问）

- **命名与层级**（2026-10-20 调整）：**项目**（需要系统性追踪、全流程管理的工作，有起止时间、联系人）→ **待办**（具体要做的一件事）→ **子步骤**（待办里的检查项）。
  - 界面叫「项目」，数据库表和代码仍叫 `tasks` / `task_id`（避免迁移数据）；新写代码时注释里写「项目」。
  - 没归入项目的待办在「零星待办」（项目页顶部、负一屏），每条有「归入项目 ›」快捷按钮（`components/move.js`）。速记时没猜到项目会显示「放入零星待办」。
  - 「全部待办」是一个查看视图（独立页面 `#/all`，可搜索），入口在首页底部「查看全部待办」和负一屏；不放在项目页（用户 2026-10-20 反馈）。旧地址 `#/tasks?view=all` 自动跳到 `#/all`。
  - 待办详情顶部显示路径「项目 › 待办」。
- **看板**（用户确认 a+b+d+e）：默认展开「进行中」「等待他人」，「未开始」「已完成」收起；顶部项目标签筛选（含零星待办）；卡片显示项目、截止、等待对象、子步骤进度；拖动换列改状态（手机长按 `LONG_PRESS_MS`=300ms 再拖，按住时卡片下沉提示）。配置集中在 `views/board.js` 顶部 `COLS` 与 `LONG_PRESS_MS`。
- **待办状态**：未开始 / 进行中 / 等待他人 / 已完成。
- **任务归档**：结束日期过后打开应用时自动归档；可在「任务」页底部恢复。
- **套用历史任务**：复制联系人、待办（标题/子步骤/标签/优先级/重复）、材料收集清单；所有日期按「新开始日 − 旧开始日」整体平移；「第N届」自动 +1。
- **等待他人与催办**：等待对象可以是人/部门/科室/单位，默认从任务联系人中选。催办时间在 `core/schedule.js`：任务时间已过 < 50% 每 3 天，50%~80% 每 2 天，> 80% 每天；固定早上 9 点。
- **提醒**：截止前（默认值在设置里改）、准时、指定时刻；早报默认 08:30、晚报默认 18:00，都可关闭。
- **材料收集**：系统只生成催办文字，由用户复制后自己发，**不代发**。
- **AI**：可开关。关闭时所有功能照常可用，AI 入口自动隐藏，且不发出任何模型请求。AI 只做增强，不能成为任何功能的前提（代码在 `data/ai.js`）：
  - 标签推荐：快速记录与详情里，在本地常用标签之外补充 AI 建议（✦ 标记）；不接 AI 也可以用「＋ 自定义标签」/「＋ 标签」手动添加（带已有标签补全）；
  - 时间识别增强：规则解析（`core/parse.js`）之后，标题里还残留时间说法（「下班前」「月底」等）才请 AI 补充；AI 失败或超时（6 秒）保持规则结果；
  - AI 对话（`components/ai-chat.js`）：首页标题行 ✦ 打开（手机底部弹出、电脑居中）。只读，不改数据；对话只在本次打开期间保留，关闭即清空。
    - 知识库（`data/knowledge.js`）：把待办（含子步骤、进展、等待对象、待发提醒）、项目（含已归档、联系人）、材料收集（含已交/未交）、联系人整理成带编号的条目（T/P/C/K + id）；每次提问在本地按关键词二字组、人名/项目名、意图词（等/催、逾期、今天/本周、收集…）挑最相关的约 24 条 + 当前概况发给模型，不额外调用 AI。
    - 回答约束（系统提示 + max_tokens=320）：≤120 字、列举最多 5 条、每条 ≤25 字、只用加粗/编号列表；引用条目时带编号，界面渲染为 ↗ 链接，点开对应待办/项目/收集；数据里没有就说没有。
    - 快捷提问 Tips：「简报」「Top 5」（各受开关控制）、「供应商还有啥没回」「等谁最久」「材料没交齐」。
  - Key 存 `user_settings.llm_api_key`（只有本人可读），从不写进代码或仓库。调用链：同源代理 → 直连 → 平台免 Key 模型。

## 8. 推送与定时提醒（P3）

**平台约束（WorkBuddy 2026-10-20 答复）**：没有自定义环境变量（只注入 PORT）；服务常驻（http-service），但平台维护时可能重启 → 服务器不能把状态放在内存或磁盘。

**组成：**

| 部分 | 文件 | 说明 |
|---|---|---|
| 添加到主屏幕 | `public/manifest.webmanifest`、`public/icons/`（`node tools/make-icons.js` 生成） | iPhone 推送的前提：iOS 16.4+，从主屏幕图标打开 |
| Service Worker | `public/sw.js` | 只负责显示通知、点击打开对应页面；不做离线缓存 |
| 订阅 | `public/app/core/pwa.js` | 设置页「开启通知」→ 请求权限 → 订阅 → 存 `push_subscriptions`（每台设备一行） |
| 加密与签名 | `server/webpush.js` | 零依赖实现 VAPID（RFC 8292）与 aes128gcm 加密（RFC 8291） |
| 通知文案 | `public/app/core/notify.js` | 前后端共用；按用户时区；点击地址：`/#/today?todo=<id>`、`/#/today`、`/#/today?review=1` |
| 调度 | `server/scheduler.js` | 每分钟一轮；「先认领再发送」保证不重复；重启后 6 小时内的提醒补发，更早的只标记；早晚报超时 3 小时不补；催办发出后自动续排 |
| 数据访问 | `server/store-db.js` + `db/migrations/002_push.sql` | 服务器在 Node 里加载与前端相同的 SDK，以 anon 身份调用带「服务器口令」校验的 SECURITY DEFINER 函数 |
| 口令来源 | `server/keys.js` | 先找 `server/server-token.txt`（方案 B），没有就等管理员登录后由应用交接（方案 C） |

SQL 已在真实 Postgres（PGlite）里跑通全部迁移并验证：错误口令被拒、认领不重复、催办不重复排、早报当天只标记一次、推送密钥只能写一次、只有管理员能取口令、anon 读不到 `server_config`。

### 8.1 服务器口令（平台无环境变量时的做法）

- 数据库表 `server_config`：开 RLS、无任何策略，前端读不到。存口令的 sha256（校验用）、口令明文（仅方案 C 用）、管理员 owner_id、推送签名密钥（服务器首次启动自动生成写入）。
- 服务器专用函数（`wb_claim_due` / `wb_schedule_nudge` / `wb_digest_candidates` / `wb_mark_digest` / `wb_remove_subscription` / `wb_server_vapid` / `wb_server_init_vapid`）第一步都校验口令；只返回推送必需的最少字段（标题、时间、状态、订阅），不返回 AI Key、备注等。
- 口令从哪来，两种方式都支持，**按部署自选**（面向部署者的完整说明与步骤：[部署与初始化.md](部署与初始化.md) 第二节）：

| 方案 | 怎么做 | 重启后 | 适合 |
|---|---|---|---|
| 口令文件 | `node tools/new-server-token.js` 生成 `server/server-token.txt` 并打印一条 SQL 交 WorkBuddy 执行；文件随部署（从 GitHub 部署时需仓库私有，并由部署者本人从 `.gitignore` 移除后提交） | 自动恢复，不漏推 | 自己用、项目只在自己手里 |
| 管理员交接（默认） | 什么都不用做。002 执行时库内自动生成口令，管理员 = 当时 `user_settings` 里最早的用户；管理员每次打开应用，应用自动把口令交给服务器（只存内存） | 暂停，直到管理员再打开应用，6 小时内的提醒随后补发 | 给同事部署、不想在仓库放密钥 |

- 接口：`GET /api/push/status`（on / locked / waiting）、`POST /api/push/unlock`（方案 C 交接，限流，校验通过才接受）。
- **重新部署 = 服务器重启**：管理员交接模式下推送会回到 locked。应用在「启动时」和「回到前台时（离开超过 30 秒）」都会自动交接，所以部署后管理员打开一次工作台即可恢复。

### 8.2 主屏幕 App 的生命周期（`core/lifecycle.js`）

- iPhone 会把主屏幕 App 挂在后台，再打开时不重新加载页面。所以回到前台时会：交接口令、重新拉数据、检查新版本。
- 下拉刷新（手机布局、页面顶部下拉）：只重新拉数据，不整页重载。
- 新版本提示：服务器启动时计算 `public/` 的指纹（`GET /api/version`）；指纹变了就在顶部提示「有新版本 · 点这里更新」，点了才整页重载。
- Service Worker 不做离线缓存，所以不存在「旧代码被缓存住」的问题；整页重载即拿到最新代码。
- **给同事部署**：见 [部署与初始化.md](部署与初始化.md) 第四节（不需要 GitHub；绝不复用别人的口令文件）。
- 换口令：重新运行 `tools/new-server-token.js` 并执行它打印的 SQL，旧口令立即失效。

## 9. 部署流程

1. 本地自检通过（§3）。
2. 更新部署所用的代码：让 WorkBuddy 从你的 Git 仓库拉取最新代码，或把项目文件夹拷到 WorkBuddy 部署所用的目录覆盖。
3. 如有新迁移文件，让 WorkBuddy 按编号逐条执行（`workbuddy_cloudservice_db_exec_sql`，mode=migrate）。
4. 让 WorkBuddy 用原配置重新部署（同一目录 → 同一应用、同一域名）。
5. 线上验证：微信登录 → 新建待办 → 改状态 → 刷新后数据还在。

全新环境或给同事部署，按 [部署与初始化.md](部署与初始化.md) 执行（含推送口令方式的选择）。

## 10. 禁止事项

- 引用任何外部 CDN；引入构建工具、框架或 npm 依赖。
- 改动 OAuth 回调路径（必须是根路径 `/`）或页面路由方式（必须用 hash）。
- 在前端代码里写死个人信息（以后可能给同事部署）。
- 绕过 `data/repos` 直接操作数据库；绕过 `run()` 吞掉错误。
- 修改已经在线上执行过的迁移文件。
- 未经用户确认就改变 §7 的业务规则。
